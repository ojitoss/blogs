# if/else management

## Why is it shit?
```js
fs.readFile(`${anweser.file}`, 'utf-8', (error, data) => {
    if (error) console.log(error);
    if (data.includes(anweser.text)) {
        console.log(true);
    } else {
        console.log(false);
    }
});
```
Do I really need to explain how a simple ```console.log(data.includes(anweser.text))``` would have been a million times better? 

Also, the code uses a completely unnecessary template string (`${anweser.file}`) instead of just passing the variable directly into the function. There are probably many more instances like this in the repo, but this one takes the prize for the most useless logic.

## How to stop being shit
This is a pretty obvious case of how beginners often forget that expressions like `data.includes()` **already return a boolean** (`true` or `false`). Writing an entire `if/else` block just to log a value that is already computed is a massive waste of lines and checks.
To fix this, stop nesting blocks inside blocks and let the expressions do the work for you. If I had written this properly back then, the whole callback could have been a clean, readable one-liner:
```js
fs.readFile(anweser.file, 'utf-8', (err, data) => {
    // ignore the error managment here, is for keep the origin feels.
    if (err) return console.error(err);
    console.log(data.includes(anweser.text));
});

```
Don't wrap booleans in `if/else` statements just to return or log those exact same booleans. It’s cleaner, shorter, and saves you from looking like you don't know how data types work.
